# 阻塞式卷纲创建机制

**卷纲创建必须完成以下验证才能输出**：

> **执行声明（强制）**
>
> - 本机制所有验证项均为**强制阻塞式**验证
> - 验证失败 → 立即停止 → 修复 → 重新验证 → 通过后才能继续
> - **禁止跳过任何验证步骤**

## 强制验证工具调用规范（关键新增）

> **目的**：通过明确指定工具调用，确保验证不会被"口头声明"绕过。

### 必须执行的工具调用

| 验证时机    | 必须调用的工具   | 验证目的            |
| ------- | --------- | --------------- |
| 表格行添加后  | `Read` 工具 | 验证表格行已添加且内容符合要求 |
| 表格完整性验证 | `Read` 工具 | 验证表格行数与规划一致     |
| 输出前     | `Read` 工具 | 最终一致性检查         |

### 工具调用验证示例

```markdown
# ✅ 正确的验证方式

[添加章节卡片表格行后]
→ 执行 `Read 02-卷纲/01-第一卷-觉醒篇.md`
→ 确认章节卡片表格中包含新行
→ 确认行内容≥50字符，包含衔接信息
→ 验证通过

[验证表格完整性时]
→ 执行 `Read 02-卷纲/01-第一卷-觉醒篇.md`
→ 统计表格行数
→ 对比：应有10章，表格有10行
→ 验证通过

# ❌ 错误的验证方式（禁止）

[添加章节卡片表格行后]
→ "已添加"（仅口头声明，无工具验证）
→ "内容完整"（仅口头声明，无工具验证）
→ ❌ 禁止：必须使用工具验证

[验证表格完整性时]
→ "所有行都存在"（仅口头声明）
→ ❌ 禁止：必须使用 Read 工具验证表格内容
```

## 多卷创建强制验证机制（关键新增）

> **最高优先级说明（强制）**：多卷创建时，必须逐卷完整验证，禁止跳过任何一卷的验证。

### 问题背景

**常见错误模式**：
- ❌ 第一卷完整创建，后续卷只创建框架
- ❌ 先为所有卷创建文件，再回头补内容（导致中间卷遗漏）
- ❌ 以"token不足"为由跳过某些卷的章节卡片表格

**跨卷事件顺序问题**（关键新增）：
- ❌ 每卷独立建立事件顺序链，不考虑前卷已完成事件
- ❌ 后续卷的事件依赖前卷未完成事件
- ❌ 跨卷事件顺序失控，导致内容超前

**跨卷事件超前示例**：
```
第一卷事件顺序链：
| 序号 | 事件名称 | 前置事件 | 最早章节 | 说明 |
| 1 | 觉醒商行 | - | 第1章 | 开篇 |
| 2 | 首次交易 | 觉醒商行 | 第2章 | 需先觉醒 |
| 3 | 商行升级 | 首次交易 | 第50章 | 需交易经验 |

第二卷（错误做法）：
| 序号 | 事件名称 | 前置事件 | 最早章节 | 说明 |
| 1 | 商行升级 | - | 第51章 | ❌ 不知道第一卷已完成到第50章 |

第二卷（正确做法）：
| 序号 | 事件名称 | 前置事件 | 前置来源 | 最早章节 | 说明 |
| 1 | 商行升级 | 首次交易 | 前卷已完成 | 第50章 | ✅ 继承前卷状态 |
| 2 | 商行扩张 | 商行升级 | 本卷 | 第60章 | ✅ 顺序正确 |
```

### 跨卷事件状态继承机制（关键新增）

> **执行要求（强制）**：创建第2卷及之后的卷纲时，必须执行跨卷事件状态继承。

```
┌─────────────────────────────────────────────────────────┐
│  🔒 跨卷事件状态继承流程                                   │
├─────────────────────────────────────────────────────────┤
│                                                          │
│ 步骤1：判断是否为跨卷创建                                  │
│     ├── 当前卷号 = 1？ → 跳过（首卷无前卷）               │
│     └── 当前卷号 > 1？ → 执行以下步骤                     │
│                                                          │
│ 步骤2：读取前卷文件                                       │
│     ├── 执行 Read 读取前卷卷纲文件                        │
│     ├── 提取前卷的"事件顺序链"表格                        │
│     └── 提取前卷的"章节卡片表格"中所有核心事件             │
│                                                          │
│ 步骤3：生成前卷事件状态表                                  │
│     ├── 格式：| 事件名称 | 完成状态 | 完成章节 | 备注 |    │
│     ├── 遍历前卷事件顺序链                                │
│     ├── 标记每个事件是否在前卷章节卡片中出现               │
│     └── 保存为"前卷事件状态表"                            │
│                                                          │
│ 步骤4：建立本卷事件顺序链（考虑前卷状态）                   │
│     ├── 识别本卷关键事件                                  │
│     ├── 建立事件依赖关系                                  │
│     ├── 检查前置事件是否在前卷已完成                     │
│     │   ├── 前置事件在前卷已完成 → 标记"前置来源：前卷已完成"│
│     │   └── 前置事件在前卷未完成 → ❌ 阻塞，不能依赖       │
│     └── 生成事件顺序链表格（含"前置来源"字段）             │
│                                                          │
│ 步骤5：实时校验（填写每章时）                               │
│     ├── 检查本卷事件是否早于前置事件                       │
│     ├── 前置来源="前卷已完成" → 无需检查前卷章节位置       │
│     └── 前置来源="本卷" → 检查前置事件是否在本卷已出现     │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

**前卷事件状态表格式**：
| 事件名称 | 完成状态 | 完成章节 | 备注 |
|----------|----------|----------|------|
| 觉醒商行 | ✅ 已完成 | 第1章 | 开篇事件 |
| 首次交易 | ✅ 已完成 | 第2章 | 需先觉醒 |
| 商行升级 | ✅ 已完成 | 第50章 | 第一卷末完成 |
| 境界突破 | ❌ 未完成 | - | 留待第二卷 |

## 常见问题与解决方案

### 问题1：表格行数与规划不符

**症状**：

- 卷纲文件中章节卡片表格行数与规划章节数不一致
- 表格缺少某些章节的行

**解决方案**：

1. 执行 `Read 02-卷纲/NN-第X卷-卷名.md` 确认表格现状
2. 按缺失章节逐行添加表格行
3. 每行添加后执行 `Read` 验证
4. 验证通过后继续添加下一行

### 问题2：表格行内容过少

**症状**：

- `Read` 显示某行内容 <50字符
- 只有章节号和标题，没有实际内容

**解决方案**：

1. 执行 `Read` 确认内容不足的行
2. 按章节卡片表格格式补充内容
3. 确保包含：衔接信息、核心事件、人物状态、爽点设计、卡点设计
4. 重新 `Read` 验证

### 问题3：衔接信息缺失

**症状**：

- `Read` 显示某行"衔接信息"字段为空或不完整

**解决方案**：

1. 执行 `Read` 找出缺失衔接信息的行
2. 补充衔接信息：
   - 第1章：承接 = "开篇"
   - 最后一章：开启 = "卷末完结"
   - 其他章：填写具体承接和开启内容
3. 重新 `Read` 验证

### 问题4：表格行内容不完整

**症状**：

- 某行缺少必填字段
- 某行字段内容为空

**解决方案**：

1. 读取卷纲文件，检查表格每行
2. 对每行检查必填字段
3. 找出缺失字段的行
4. 补充缺失字段内容
5. 重新执行阶段四验证

***

**记住**：

> "验证不是可选的，而是强制阻塞的。使用工具验证，而不是口头声明。"
